# Формат DTCG и трёхуровневая архитектура токенов

DTCG (Design Tokens Community Group) — стандартный JSON-формат для дизайн-токенов: `$type`, `$value`, опционально `$description`. Его понимают Figma Variables, Style Dictionary, Tokens Studio — то есть токены в этом формате переносимы между инструментами, а не привязаны к одному стеку.

```json
{
  "blue": {
    "500": {
      "$type": "color",
      "$value": "oklch(58% 0.18 250)",
      "$description": "Primary brand blue — base shade, 4.5:1+ on white"
    }
  }
}
```

## Три уровня — и почему их нельзя смешивать

**Primitive (примитив).** Сырые значения без смысла использования: `blue.500`, `space.4`, `duration.200`. Никогда не используются в коде напрямую — только как источник для алиасов ниже.

**Semantic (семантика).** Алиасы на примитивы, названные по назначению, не по значению: `color.action.primary` → `{blue.500}`, `space.gap.default` → `{space.4}`. Это уровень, который меняется при смене темы (light/dark) — примитив остаётся, семантика переключает, на что он указывает.

**Component (компонент).** Алиасы, привязанные к конкретному UI-элементу: `button.background.default` → `{color.action.primary}`, `button.background.hover` → `{color.action.primary.hover}`. Меняется только для одного компонента, не трогая всю систему.

**Правило:** код и вёрстка ссылаются только на component- или semantic-токены, никогда на primitive напрямую. Если в CSS/коде встретился хардкод цвета или отступа вместо ссылки на токен — это то, что ловит `scripts/validate_tokens.py` косвенно (через отсутствие алиаса) и что стоит проверять глазами при ревью кода.

## Файлы и структура

Обычно один файл на категорию токенов в директории `tokens/` в корне проекта: `colors.json`, `typography.json`, `spacing.json`, `shadows.json`, `borders.json`, `motion.json`, `theming.json` и так далее — не обязательно все сразу, начинай с того, что реально нужно для задачи (для лендинга не нужны `blur.json` и `theming.json` с нуля).

## Отступы: единая база

Возьми одну базовую единицу (обычно 4px) и стройте шкалу от неё кратными шагами — так отступы в макете и в коде остаются на одной сетке, и не появляются случайные 13px или 22px из "показалось, что так лучше".

```json
{
  "space": {
    "1": { "$type": "dimension", "$value": "4px" },
    "2": { "$type": "dimension", "$value": "8px" },
    "3": { "$type": "dimension", "$value": "12px" },
    "4": { "$type": "dimension", "$value": "16px" },
    "6": { "$type": "dimension", "$value": "24px" },
    "8": { "$type": "dimension", "$value": "32px" },
    "12": { "$type": "dimension", "$value": "48px" },
    "16": { "$type": "dimension", "$value": "64px" }
  }
}
```

## Типографическая шкала

Одно из модульных отношений (Major Third — 1.25, Perfect Fourth — 1.333 и т.д.) применённое к базовому размеру (обычно 16px) — так весь текст на странице подчинён одной прогрессии, а не набору интуитивных размеров.

```json
{
  "fontSize": {
    "base": { "$type": "dimension", "$value": "16px" },
    "md":   { "$type": "dimension", "$value": "20px", "$description": "base × 1.25" },
    "lg":   { "$type": "dimension", "$value": "25px", "$description": "md × 1.25" },
    "xl":   { "$type": "dimension", "$value": "31px", "$description": "lg × 1.25" }
  }
}
```

## Генерация цветовой палитры с гарантией контраста

Если задача — сделать полноценную палитру бренд-цвета (не один hex, а рабочий ряд оттенков), генерируй 11 шейдов в OKLCH (он перцептивно равномерный — шаг между соседними шейдами выглядит одинаковым, в отличие от HSL) от `50` (самый светлый) до `950` (самый тёмный), и сразу проверяй ключевые контрастные пары скриптом:

```bash
python3 scripts/contrast.py "<hex шейда 500>" "#ffffff"
python3 scripts/contrast.py "<hex шейда 600>" "#ffffff"
```

**Обязательные пороги** (не эстетическая рекомендация, а требование WCAG для текста и интерфейсных элементов):
- шейд `500` — не ниже 4.5:1 на белом (это будет твой основной текстовый/акцентный оттенок)
- шейд `600` — не ниже 3:1 на белом (это будет твой оттенок для границ/иконок/UI-элементов)

Если сгенерированный оттенок не проходит порог — не публикуй его как есть, сдвинь lightness в OKLCH до прохождения, и только потом фиксируй в токенах. Здесь именно измеренная проверка скриптом, а не «на глаз похоже что контрастно».

## Валидация

После любых изменений в `tokens/*.json`:

```bash
python3 scripts/validate_tokens.py
```

Скрипт проверяет: (1) каждый файл — валидный JSON, (2) каждый алиас вида `{colors.blue.500}` резолвится в реально существующий токен. Незарезолвленный алиас — это токен, который в коде тихо развалится или вернёт `undefined`, лучше поймать здесь, чем в браузере у клиента.
